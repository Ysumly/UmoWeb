# UmoWeb 四阶段后续路线

> **For agentic workers:** 本文件是阶段路线图，不是单个功能的代码级实施计划。每个功能开始实现前，仍需先完成对应设计，再使用 `superpowers:writing-plans` 拆成可执行任务。

**Goal:** 按正式上线、工程交付、功能设计、AI 探索四个阶段推进 UmoWeb，避免把上线事项、功能设计和未成熟的 AI 需求混在同一优先级中。

**Architecture:** 第一阶段闭环正式部署和数据安全；第二阶段补齐 CI、真实数据库集成、镜像交付、回滚和访问信息统计；第三阶段先设计并实现内容、检索、媒体和训练游戏功能；第四阶段仅在需求明确后接入 AI。

**Tech Stack:** Vue 3、Vite 8、Playwright、Spring Boot 4.1、Java 17、MyBatis、MySQL 8.4、Docker Compose、Nginx。

**Spec:** `docs/project/codebase-memory.md`、`docs/project/docker-guide.md`、`docs/design/personal-blog-srs.md`

## Global Constraints

- 当前代码行为是唯一事实来源，计划能力不得写成已实现能力。
- 阶段按顺序推进；前一阶段未通过出口条件时，不把后一阶段功能混入正式发布范围。
- 每个功能在编码前必须有独立设计，明确接口、数据迁移、失败处理、测试和回滚策略。
- 正式域名、实例标识、公网地址、管理路径、管理员密码、数据库密码和 JWT secret 不进入仓库。
- 修改接口、Schema、前端依赖、测试范围或部署方式时，按 `development-workflow.md` 的文档同步矩阵更新。
- 每个可独立验收的任务完成后分别提交并推送，不把多个阶段压成一次提交。

## 第二阶段：工程交付、质量基线与安全统计

**阶段目标:** 把当前依赖人工执行的构建、测试、镜像交付和回滚流程固化为可重复的 CI/CD 链路，并建立以安全和运维为目的的最小化访问统计。

**Dependencies:** 第一阶段应已完成；如 CI 提前开发，只能用于非正式环境，不能替代正式上线阻断项。

### Task 2.1: 建立 CI 基础流水线

**状态:** 已完成（2026-09-13）。基础检查已接入 GitHub Actions，依赖
[`../../project/testing-guide.md`](../../project/testing-guide.md) 第 2.8 节。

**Deliverable:** 拉取请求和 `master` 分支自动执行基础质量检查。

所需检查：

- 后端 `mvn test`。

因此失败结果不能自动阻止合并；Task 2.4 必须把 CI 成功作为镜像发布的前置条件。

**状态:** 已完成（2026-09-13）。GitHub Actions 使用 MySQL 8.4 从空库验证

### Task 2.4: 固定镜像发布与回滚流程

**状态:** 已完成（2026-09-13）。本地发布/回滚脚本和自测已实现，并完成 ECS
`v1.0.0-rc.1` 发布、baseline 回滚和 rc.1 恢复演练。

**Deliverable:** 可追溯的镜像、版本标签、发布命令和回滚命令。

- 不引入长期镜像仓库；开发机保存版本归档，ECS 只保留当前运行镜像和最少状态。
- 前后端镜像同时打 Git commit 和发布版本标签，并记录 image ID、归档 SHA-256 和 manifest。
- 发布前检查健康状态，发布后执行公网首页、公开 API、管理员登录和容器健康验证。
- 回滚时从开发机上传上一版本归档，不重新构建。
- 完成标准：从上一版本完成一次发布和一次回滚演练，耗时和命令写入部署文档。

### Task 2.5: 访问信息统计与安全日志

**状态:** 已完成（2026-09-13）。`v1.0.0-rc.3` 已部署；Nginx 六字段日志、主机级聚合与
127.0.0.1 静态报表、公开隐私说明和发布 manifest 访问策略均通过 ECS 验收。

**Deliverable:** 一套只记录最少必要字段、短期保留原始日志并根据匿名聚合生成报表的自托管安全统计链路。

**适用边界:**

- 访问信息只用于站点安全、故障排查和运维分析，不用于广告、用户画像或跨站追踪。
- 默认不引入第三方分析平台，不把原始日志发送给广告平台或无法控制的数据服务商。
- 第一阶段确定最终 HTTPS 和代理拓扑后，访问统计必须复用同一套可信代理规则取得客户端 IP。

#### 原始访问日志

- Nginx 使用专用最小日志格式，字段严格限制为客户端 IP、ISO 8601 时间、HTTP 方法、
  仅路径、状态码和响应字节数。
- 路径字段使用不带查询字符串的 `$uri`，不记录 `$request`、`$args`、请求体、密码、
  Token、Cookie、Authorization、Referer 或 User-Agent。
- 后端不重复输出完整 HTTP access log，应用错误日志继续避免输出请求体和凭据。
- 只在直连来源匹配可信代理配置时采用转发头解析客户端 IP；不能把客户端伪造的
  `X-Forwarded-For` 直接写入安全日志。

**保存与删除:**

- 原始访问日志默认保留 30 天，允许配置为 7 至 30 天，超出配置范围必须拒绝启动或明确失败。
- 使用每日自动轮转和自动删除，不依赖人工清理；删除策略需要覆盖压缩归档文件。
- 日志目录只允许部署账户和管理员访问，推荐目录权限 `0750`、文件权限 `0640`。
- 日志目录、报表卷和部署凭据都不进入 Git，也不映射到公网。

#### 长期聚合

- 长期只保存聚合结果，例如每日独立 IP 数量、请求总数、状态码分布、响应字节数和访问路径排行。
- 聚合保存前丢弃原始 IP、完整请求路径以外的敏感信息以及任何可用于跨日追踪原始 IP 的标识。
- 聚合结果默认保留 180 天并支持配置；隐私说明中的保留期限必须与实际配置一致。
- 长期聚合文件不得包含 IPv4、IPv6 或具体客户端地址。

#### 报表访问

- 推荐使用自托管 GoAccess 读取保留期内的原始日志，生成短期安全和运维报表。
- 报表服务只绑定 `127.0.0.1`，由管理员通过 SSH 隧道访问；不新增公网端口，不进入公开导航。
- 如后续提供管理端报表页面，必须复用管理员认证和授权，并禁止匿名、缓存和搜索引擎索引。
- 不启用会长期保存原始 IP 的 GoAccess 持久化数据库；需要长期指标时只落盘匿名聚合结果。
- 如短期报表产物包含原始 IP，只保存在管理员权限目录并随原始日志使用同一保留期限删除；
  不把报表文件作为长期归档。

#### 隐私说明

- 公开隐私说明必须写明收集目的、最小字段、使用范围、原始日志保留期、聚合保留期和管理员访问边界。
- 隐私说明明确不把原始访问日志交给广告平台或无法控制的数据服务商。
- 未来接入 Cloudflare、第三方统计、集中日志平台或跨区域服务器前，必须重新评估数据流向、
  数据控制方、访问权限和跨境传输，不得直接沿用当前方案。

**验证要求:**

- 构造包含密码、Token、Cookie、敏感查询参数和请求体的请求，验证访问日志只包含约定的六个字段。
- 验证带查询字符串的搜索和登录请求只记录路径，不记录查询值。
- 从非可信来源伪造 `X-Forwarded-For`，验证限流和日志都使用直连地址，不采用伪造值。
- 使用合成旧日志验证每日轮转、压缩和 7、30 天边界删除，确认不存在超期原始文件。
- 检查日志目录、聚合目录和报表端口的权限，普通用户和公网均不能读取或访问。
- 扫描长期聚合文件，确认不包含原始 IP。
- 在隐私说明与运行配置之间执行交叉检查，确认字段、用途和保留期一致。

### 第二阶段出口条件

- 基础测试、Playwright、MySQL 集成和构建都能在 CI 中自动运行。
- 正式环境由版本化镜像发布，发布与回滚不需要临时修改代码。
- 部署记录能回答“当前运行的是哪个 commit、哪个 digest、由哪次流水线产生”。
- 访问统计只保留最小字段，原始日志按 7 至 30 天自动删除，长期只保留匿名聚合。
- GoAccess 或等价报表只允许管理员访问，日志、报表和长期数据均未暴露到公网。
- 隐私说明已经公开，并与实际采集字段、用途和保留策略一致。

## 第三阶段：功能设计阶段

**阶段目标:** 完善内容生产、内容检索、分类筛选、媒体管理和训练游戏等必要产品能力。

**Dependencies:** 第一、二阶段完成，正式内容和可回滚部署已经稳定。

**执行规则:** 本阶段每个子功能先完成设计和接口评审，再拆分代码级计划。图片删除、全文搜索和子分类筛选不得再被描述为第一阶段遗留缺陷，它们属于第三阶段正式功能。

### Task 3.1: 管理端 Markdown 导入

**状态:** 已完成（2026-09-13）。新建文章页支持单文件 `.md`/`.markdown` 导入；YAML front matter
可预填现有表单，缺失字段按 H1、文件名和默认值回退。导入继续复用文章创建接口，不新增 API。

**设计问题:**

- 先支持单文件导入还是直接支持批量导入；推荐先完成单文件，再复用解析结果扩展批量。
- 文件正文、H1、文件名、front matter 与现有 DTO 字段之间如何映射。
- 新建与更新冲突如何处理；建议默认拒绝覆盖，并提供显式替换选项。
- 相对图片、远程图片和本地图片引用如何处理；不支持时必须给出导入前提示。
- 导入过程如何复用现有临时文件、数据库回滚恢复和提交后清理策略。

**最低功能边界:**

- 管理端可选择 `.md` 文件并预览标题、slug、类型、状态、分类、标签和摘要。
- 导入成功后内容能进入公开端或作为草稿保存。
- 重复 slug、非法 metadata、缺失分类和文件写入失败均返回可理解的错误。
- 不允许导入内容绕过现有长度、路径、枚举和文件安全校验。

**验收要求:**

- 后端单元与事务边界测试覆盖成功、冲突和回滚。
- 真实 MySQL 与临时存储验证数据库和 Markdown 文件同时正确。
- 管理端 Playwright 覆盖选择、预览、确认、错误和跳转编辑。
- API 或请求契约变化时同步 `api-reference.md`、模块文档和审计记录。

### Task 3.2: 分类筛选包含子分类

**状态:** 已完成（2026-09-13）。公开端和管理端列表新增 `includeDescendants`，默认继续保持
`categoryId` 精确匹配；启用后按分类树展开全部后代。书库分类筛选默认包含后代，循环或超过 32 层
返回 409，真实 MySQL 测试和双冒烟脚本已覆盖。

**设计问题:**

- 保持现有精确匹配兼容，还是修改默认语义；推荐新增显式的包含后代参数，避免破坏现有调用方。
- 父分类、子分类和后代内容如何稳定排序与去重。
- 分类循环防护和层级深度上限如何约束查询成本。

**验收要求:**

- Mapper 集成测试覆盖根分类、两级后代、空结果和循环数据拒绝。
- 公开 API 与书库 URL 参数保持同步，分类未选中时不改变返回结果。
- 更新查询语义文档、接口文档和前端筛选测试。

### Task 3.3: 图片删除与引用保护

**状态:** 已完成（2026-09-13）。新增管理端图片列表与删除接口，保护全部文章状态和
About/Project 引用；文件清理使用持久队列并在启动或后续图片操作前重试。

**设计问题:**

- 新增删除接口的路径、权限和成功状态；按现有约定删除成功应为 204。

### Task 4.1: AI 产品设计

候选方向只用于需求讨论，不预设实现：

- 编辑器辅助润色、摘要、标题建议或标签建议。
- 基于已发布内容的问答或语义检索。
- 内容草稿的结构检查和缺失信息提示。

设计必须回答：

- 用户使用场景、成功指标和明确不做的范围。
- 哪些内容允许发送给模型，是否包含草稿、私有内容和上传图片。
- 模型供应商、数据保留策略、区域合规、成本上限、超时和降级方案。
- 输出如何审核、引用、审计和撤销，如何防止 Prompt Injection。
- AI 失败时如何保证现有编辑、发布和搜索功能不受影响。

### Task 4.2: AI 独立设计评审

- 先形成独立设计文档，不直接修改现有内容接口。
- 通过后拆分为后端边界、前端交互、数据隐私、提示词评测和成本监控任务。
- 完成标准：需求、隐私、安全和成本均有明确结论，没有结论前不进入编码。

### 第四阶段出口条件

- AI 功能有真实用户价值和明确成功率指标。
- 隐私、成本、降级和审计方案经过评审。
- 功能不影响现有非 AI 路径，并有可重复的评测集。
