# UmoWeb 四阶段后续路线

> **For agentic workers:** 本文件是阶段路线图，不是单个功能的代码级实施计划。每个功能开始实现前，仍需先完成对应设计，再使用 `superpowers:writing-plans` 拆成可执行任务。

**Goal:** 按正式上线、工程交付、功能设计、AI 探索四个阶段推进 UmoWeb，避免把上线事项、功能设计和未成熟的 AI 需求混在同一优先级中。

**Architecture:** 第一阶段闭环正式部署和数据安全；第二阶段补齐 CI、真实数据库集成、镜像交付和回滚；第三阶段先设计并实现内容、检索、媒体和训练游戏功能；第四阶段仅在需求明确后接入 AI。

**Tech Stack:** Vue 3、Vite 8、Playwright、Spring Boot 4.1、Java 17、MyBatis、MySQL 8.4、Docker Compose、Nginx。

**Spec:** `docs/project/codebase-memory.md`、`docs/project/docker-guide.md`、`docs/design/personal-blog-srs.md`

## Global Constraints

- 当前代码行为是唯一事实来源，计划能力不得写成已实现能力。
- 阶段按顺序推进；前一阶段未通过出口条件时，不把后一阶段功能混入正式发布范围。
- 每个功能在编码前必须有独立设计，明确接口、数据迁移、失败处理、测试和回滚策略。
- 正式域名、实例标识、公网地址、管理路径、管理员密码、数据库密码和 JWT secret 不进入仓库。
- 修改接口、Schema、前端依赖、测试范围或部署方式时，按 `development-workflow.md` 的文档同步矩阵更新。
- 每个可独立验收的任务完成后分别提交并推送，不把多个阶段压成一次提交。

## 当前完成基线

以下能力已经实现并有验证记录，不作为后续阶段的新增任务：

- 公开端阅读主路径、公开 Markdown 编辑器和全部管理端核心业务页。
- 27 个真实接口和 27/27 冒烟验证。
- 后端 83 个测试、前端 46 个 Node 测试和 34 个 Playwright 检查。
- Docker Compose 全栈和单台阿里云 ECS 无域名 HTTP 测试部署。
- 隔离 MySQL 5.7 迁移演练和 Docker MySQL 8.4 持久化验证。

当前部署仍使用演示数据，没有正式域名、HTTPS、自动备份、恢复演练或 CI/CD。

## 第一阶段：正式上线与数据安全

**阶段目标:** 在可恢复、可回滚的前提下替换演示数据，并通过域名和 HTTPS 提供正式服务。

**Dependencies:** 无。当前公网部署、数据库和 `app_data` 卷是输入。

### Task 1.1: 冻结正式发布范围

**Deliverable:** 一份发布检查清单，明确上线功能、排除项、负责人、验收环境和回滚触发条件。

- 确认上线范围只包含现有公开端和管理端能力。
- 明确图片删除、全文搜索、子分类筛选、Markdown 导入和训练游戏不在第一阶段上线范围。
- 记录正式域名的 DNS 归属和证书续期方式，但不把域名解析权限写入仓库。
- 完成标准：发布检查清单可逐项勾选，任何未完成项都有明确阻断或接受理由。

### Task 1.2: 建立备份与恢复闭环

**Deliverable:** MySQL 和 `app_data` 的可重复备份、恢复及校验流程。

- 备份 MySQL 逻辑数据，并保存数据库版本、时间、文件大小和 SHA-256。
- 备份 `app_data` 中的 Markdown 和上传图片，保留相对路径和文件清单。
- 在隔离 Compose 项目或隔离目录中恢复，禁止直接覆盖正式卷验证。
- 校验恢复后的表行数、关键记录、Markdown 文件数量和图片文件数量。
- 恢复环境执行 `api-smoke.ps1`，要求 27/27 通过。
- 完成标准：从空环境恢复成功，记录备份耗时、恢复耗时、校验结果和失败处理步骤。

### Task 1.3: 导入正式内容并轮换凭据

**Deliverable:** 正式内容可读取、演示数据不再作为业务数据、全部部署凭据已轮换。

- 正式环境不要自动导入演示 Markdown 或演示管理员。
- 使用已经演练通过的备份恢复流程导入正式内容和站点配置。
- 轮换管理员密码、数据库密码和 JWT secret；旧 JWT 必须立即失效。
- 核对公开端只返回 `PUBLISHED` 内容，管理端能看到草稿和已发布内容。
- 完成标准：公开内容、分类、标签、站点设置、图片和 About/Project 均来自正式数据。

### Task 1.4: 域名、HTTPS 与真实客户端 IP

**Deliverable:** HTTPS 正式入口，HTTP 自动跳转，CORS 和限流使用正确来源。

- 在宿主 Nginx + Certbot 与容器化 Caddy 两种方案中选择一种，并记录证书续期和故障恢复方式。
- 只暴露 HTTPS；HTTP 只保留跳转到 HTTPS 所需的入口。
- 将 `CORS_ALLOWED_ORIGINS` 更新为正式 HTTPS 来源。
- 验证最终代理拓扑下登录和搜索限流能取得真实客户端 IP，伪造 `X-Forwarded-For` 不能绕过限流。
- 完成标准：证书有效、续期演练通过、无混合内容、401/429 和静态资源在 HTTPS 下行为正确。

### 第一阶段出口条件

- 备份恢复演练通过，正式数据与文件均在恢复验证之后导入。
- HTTPS 公网入口通过验收，演示数据和默认凭据不再生效。
- 正式环境完成 27/27 接口冒烟和管理员登录验证。
- 发布回滚点和回滚步骤已经实测。

## 第二阶段：工程交付与质量基线

**阶段目标:** 把当前依赖人工执行的构建、测试、镜像交付和回滚流程固化为可重复的 CI/CD 链路。

**Dependencies:** 第一阶段应已完成；如 CI 提前开发，只能用于非正式环境，不能替代正式上线阻断项。

### Task 2.1: 建立 CI 基础流水线

**Deliverable:** 拉取请求和 `master` 分支自动执行基础质量检查。

所需检查：

- 后端 `mvn test`。
- 前端 `npm test`。
- 前端 `npm run build`。
- 文档敏感信息扫描和 `git diff --check`。

完成标准：干净检出可以稳定复现四类检查；任一检查失败会阻止合并或阻止镜像发布。

### Task 2.2: 接入 Linux Playwright 与独立视觉基线

**Deliverable:** 浏览器功能测试和 Linux 视觉基线在 CI 中可重复执行。

- CI 使用 Playwright 固定版本和 Linux Chromium，不依赖开发机 Chrome channel。
- Linux 视觉快照使用独立文件，不覆盖当前 Windows 基线。
- 浏览器测试继续使用明确的 Mock API，真实接口由数据库集成任务负责。
- 完成标准：连续两次 CI 运行结果一致，浏览器升级造成的基线变化有独立更新流程。

### Task 2.3: 增加真实 MySQL 集成验证

**Deliverable:** CI 自动验证 Schema、种子迁移、Mapper SQL 和完整接口链。

- 使用 MySQL 8.4 服务容器执行 `schema.sql` 和迁移脚本。
- 后端连接真实数据库启动，并执行 `api-smoke.ps1`。
- 覆盖公开过滤、分类与标签关联、详情邻居、文件上传、JWT 失效和 429。
- 测试上传文件使用临时卷，任务结束后销毁。
- 完成标准：CI 中 27/27 冒烟通过，不能再只依赖开发机手工记录。

### Task 2.4: 固定镜像发布与回滚流程

**Deliverable:** 可追溯的镜像、版本标签、发布命令和回滚命令。

- 选择阿里云 ACR 或仓库可稳定访问的私有镜像仓库，不再依赖人工传包作为长期方案。
- 前后端镜像同时打 Git commit 和发布版本标签，并记录镜像 digest。
- 发布前检查健康状态，发布后执行公网首页、公开 API、管理员登录和容器健康验证。
- 回滚时使用上一组已记录的镜像 digest，不重新构建。
- 完成标准：从上一版本完成一次发布和一次回滚演练，耗时和命令写入部署文档。

### 第二阶段出口条件

- 基础测试、Playwright、MySQL 集成和构建都能在 CI 中自动运行。
- 正式环境由版本化镜像发布，发布与回滚不需要临时修改代码。
- 部署记录能回答“当前运行的是哪个 commit、哪个 digest、由哪次流水线产生”。

## 第三阶段：功能设计阶段

**阶段目标:** 完善内容生产、内容检索、分类筛选、媒体管理和训练游戏等必要产品能力。

**Dependencies:** 第一、二阶段完成，正式内容和可回滚部署已经稳定。

**执行规则:** 本阶段每个子功能先完成设计和接口评审，再拆分代码级计划。图片删除、全文搜索和子分类筛选不得再被描述为第一阶段遗留缺陷，它们属于第三阶段正式功能。

### Task 3.1: 管理端 Markdown 导入

**设计问题:**

- 先支持单文件导入还是直接支持批量导入；推荐先完成单文件，再复用解析结果扩展批量。
- 文件正文、H1、文件名、front matter 与现有 DTO 字段之间如何映射。
- 新建与更新冲突如何处理；建议默认拒绝覆盖，并提供显式替换选项。
- 相对图片、远程图片和本地图片引用如何处理；不支持时必须给出导入前提示。
- 导入过程如何复用现有临时文件、数据库回滚恢复和提交后清理策略。

**最低功能边界:**

- 管理端可选择 `.md` 文件并预览标题、slug、类型、状态、分类、标签和摘要。
- 导入成功后内容能进入公开端或作为草稿保存。
- 重复 slug、非法 metadata、缺失分类和文件写入失败均返回可理解的错误。
- 不允许导入内容绕过现有长度、路径、枚举和文件安全校验。

**验收要求:**

- 后端单元与事务边界测试覆盖成功、冲突和回滚。
- 真实 MySQL 与临时存储验证数据库和 Markdown 文件同时正确。
- 管理端 Playwright 覆盖选择、预览、确认、错误和跳转编辑。
- API 或请求契约变化时同步 `api-reference.md`、模块文档和审计记录。

### Task 3.2: 分类筛选包含子分类

**设计问题:**

- 保持现有精确匹配兼容，还是修改默认语义；推荐新增显式的包含后代参数，避免破坏现有调用方。
- 父分类、子分类和后代内容如何稳定排序与去重。
- 分类循环防护和层级深度上限如何约束查询成本。

**验收要求:**

- Mapper 集成测试覆盖根分类、两级后代、空结果和循环数据拒绝。
- 公开 API 与书库 URL 参数保持同步，分类未选中时不改变返回结果。
- 更新查询语义文档、接口文档和前端筛选测试。

### Task 3.3: 图片删除与引用保护

**设计问题:**

- 新增删除接口的路径、权限和成功状态；按现有约定删除成功应为 204。
- Markdown 中已引用图片时如何阻止误删；推荐扫描正式内容引用并返回 409。
- 图片记录删除成功但文件清理失败时如何重试和记录。
- 管理端如何展示引用状态，以及是否提供孤立图片筛选。

**验收要求:**

- 后端覆盖未引用删除、已引用 409、文件失败、记录不存在和无权限。
- 数据删除与文件删除复用现有“数据库提交/回滚、提交后清理”策略。
- 管理端 Playwright 覆盖删除确认、409 提示和列表刷新。
- 冒烟脚本使用独立临时图片，并在结束后验证清理结果。

### Task 3.4: Markdown 正文全文搜索

**设计问题:**

- 标题、摘要与 Markdown 正文如何形成统一搜索文本。
- 中文分词使用 MySQL FULLTEXT `ngram`、独立搜索表，还是外部搜索服务；当前推荐先用 MySQL 8.4 `ngram`，避免引入额外基础设施。
- 正文索引在创建、更新、发布、撤回和删除时如何同步，失败时如何回填。
- 搜索排序、摘要高亮、分页和现有 429 限流如何组合。

**最低功能边界:**

- 公开搜索覆盖标题、摘要和正文，只返回 `PUBLISHED`。
- 旧内容可通过一次性回填建立索引，回填可重复执行。
- 搜索普通响应保持无统一包装，错误响应继续使用 `{ code, message }`。
- 前端展示与正文命中相关的可理解摘要，不返回未发布内容。

**验收要求:**

- Schema 迁移、回填脚本和幂等验证纳入 MySQL 集成测试。
- 创建、更新、撤回和删除内容后，索引行为有服务层与真实数据库测试。
- Playwright 覆盖普通搜索、无结果、429 倒计时和移动端结果布局。
- 搜索语义仍使用 title/summary 的旧文档必须全部校正，避免文档与代码冲突。

### Task 3.5: 四个训练游戏

四个输入文件当前是独立静态 HTML，包含内联 CSS/JS 和 `localStorage` 成绩；除 Google Fonts 外没有外部服务调用。

**固定输入与 SHA-256:**

| 游戏 | 源文件 SHA-256 |
|---|---|
| Stroop 色词测试 | `100535847DBC76F082CA023F33BAE2CA925782268B382E6CA7EE56F6CDEE776C` |
| 倒背数字训练 | `80E469C5099720007B062962259149780409C451D6824B212FDA9A8776C32ED2` |
| 扑克牌记忆训练 | `22757B8FCD86A516B1DDBBA784FEE472C6E6DC3C61D51D3CACBEA2064A627D2C` |
| 舒尔特网格小游戏 | `5C31758C96BE3E931DB875DA31F763B6C54E2B04F05C6BFFBFBC0E00F8529350` |

**设计问题:**

- 推荐迁移为 Vue 路由和共享游戏外壳，不直接复制整页 HTML；保留游戏规则和纯函数逻辑，统一站点主题、响应式布局和返回路径。
- 建议路由为 `/games`、`/games/stroop`、`/games/digit-span`、`/games/poker-memory` 和 `/games/schulte`。
- 默认只把最佳成绩保存在浏览器；排行榜、账号同步和云端存档不属于第三阶段，若需要必须新增设计。
- 继续兼容现有 `stroop_84_parchment`、`poker_memory_best_span` 和 `schulte_parchment_best` 键；倒背数字当前没有持久化成绩。
- 移除 Google Fonts 远程依赖，使用站点字体资源，避免隐私、离线和新窗口布局偏移。

**最低功能边界:**

- 四个游戏保持原有主要玩法、计分规则和重开流程。
- 桌面和移动端均有清晰开始、进行中、反馈和结束状态。
- 键盘、触控和减少动态偏好下可操作；关键按钮有可访问名称。
- 离开进行中的游戏时给出明确处理，定时器、动画和事件监听在卸载时清理。

**验收要求:**

- 随机数、计分和最佳成绩等纯逻辑使用 Node 单元测试，必要时注入随机源保证确定性。
- Playwright 覆盖开始、作答、错误反馈、重开、成绩保存和刷新恢复。
- 桌面与移动端视觉快照覆盖每个游戏，并检查横向溢出。
- 更新前端路由、架构、依赖和页面状态文档，明确游戏是否使用后端。

### 第三阶段推荐顺序

1. Markdown 导入，先固定内容进入系统的统一路径。
2. 分类子级筛选，复用现有内容查询模型。
3. 图片删除与引用保护，补齐媒体生命周期。
4. 全文搜索，必须在 Markdown 导入和正文索引契约确定后实施。
5. 四个训练游戏，完成独立设计后可与其他功能并行实施。

### 第三阶段出口条件

- 内容可以通过编辑器或 Markdown 文件可靠进入系统。
- 正文搜索、子分类筛选和图片删除都有真实数据库、文件系统和浏览器验证。
- 四个游戏已进入统一前端体验，不残留依赖旧 `index.html` 的孤立入口。
- 所有新增接口、Schema、前端依赖和用户流程均同步文档。

## 第四阶段：AI 能力

**阶段目标:** 在第三阶段完成且产品需求明确后，决定是否以及如何集成 AI。

**Dependencies:** 第三阶段出口条件全部满足；AI 使用场景、数据边界和成本上限已经确认。

**当前状态:** Spring AI 依赖存在，但当前业务代码没有调用，不把“已引入依赖”视为已接入 AI。

### Task 4.1: AI 产品设计

候选方向只用于需求讨论，不预设实现：

- 编辑器辅助润色、摘要、标题建议或标签建议。
- 基于已发布内容的问答或语义检索。
- 内容草稿的结构检查和缺失信息提示。

设计必须回答：

- 用户使用场景、成功指标和明确不做的范围。
- 哪些内容允许发送给模型，是否包含草稿、私有内容和上传图片。
- 模型供应商、数据保留策略、区域合规、成本上限、超时和降级方案。
- 输出如何审核、引用、审计和撤销，如何防止 Prompt Injection。
- AI 失败时如何保证现有编辑、发布和搜索功能不受影响。

### Task 4.2: AI 独立设计评审

- 先形成独立设计文档，不直接修改现有内容接口。
- 通过后拆分为后端边界、前端交互、数据隐私、提示词评测和成本监控任务。
- 完成标准：需求、隐私、安全和成本均有明确结论，没有结论前不进入编码。

### 第四阶段出口条件

- AI 功能有真实用户价值和明确成功率指标。
- 隐私、成本、降级和审计方案经过评审。
- 功能不影响现有非 AI 路径，并有可重复的评测集。
